Sesión 6 · Los comandos de la sesión y su salida

Data-driven AI: análisis y normalización · Máster en AI Engineering (LIDR). Cada script y comando que se usa en el directo, en orden: para qué sirve, cómo se lanza, la salida real (ejecutada en local sobre la rama session_06_live) y cómo leerla. La referencia «diapo N» indica dónde aparece en las diapositivas.

0 · Preparar el entorno

Todos los comandos se lanzan desde la raíz del repositorio (donde está docker-compose.yml), en la rama session_06_live. El código Python se ejecuta dentro del contenedor estimator con docker compose exec, así que no hace falta instalar nada en el ordenador. Si levantaste el stack con un nombre de proyecto propio (docker compose -p mi-nombre up), añade ese -p mi-nombre a cada docker compose. Ninguno de estos comandos llama a un modelo de IA: se pueden repetir sin coste.

2.1 · CAG, RAG o híbrido

python -m app.ingestion.architecture
diapo 7
Para qué sirve. Convierte la decisión del Article 1 en código que se ejecuta. Describe el corpus del Proyecto 2 y el modelo (PROYECTO_2 y CURRENT_MODEL en app/ingestion/architecture.py), evalúa las cuatro restricciones del CAG y recomienda una arquitectura.
Comando
docker compose exec estimator python -m app.ingestion.architecture
Salida
Corpus 'Proyecto 2': 250,000 tokens, refresh cada 7 días, trazabilidad=True, control_acceso=True
Modelo 'gpt-4o-mini': ventana 128,000 tokens, prefix_caching=True

Viabilidad CAG: NO viable
  Restricciones en rojo: context_window, latency, lost_in_the_middle
Recomendación arquitectónica: RAG
Cómo leerla.
  • NO viable: basta con que una restricción esté en rojo (viable es un all([...])).
  • context_window: 250.000 tokens no caben en el 70 % útil de 128.000.
  • latency y lost_in_the_middle: por encima de 100.000 tokens el código asume que la latencia se dispara y el centro del contexto se atiende peor.
  • cost no sale en rojo: hay caché de prefijo y el corpus cambia cada 7 días.
Prueba tú: cambiar el escenario
diapo 8
Para qué sirve. Las funciones son puras: puedes evaluar tu propio corpus sin tocar el fichero. Abre un intérprete dentro del contenedor con docker compose exec estimator python y pega:
Comando
from app.ingestion.architecture import *
for name, tok, ref, citar, acceso in [
        ("Pequeño y estable", 60_000, 30, False, False),
        ("Pequeño pero hay que citar", 60_000, 30, True, False),
        ("Proyecto 2", 250_000, 7, True, True)]:
    c = CorpusProfile(name, tok, ref, citar, acceso)
    v = assess_cag_viability(c, CURRENT_MODEL)
    print(name, v.viable, v.failing_constraints(), recommend_architecture(c, CURRENT_MODEL))
Salida
Pequeño y estable           60,000 tokens · citar=False · acceso=False → viable=True  rojo=[] → CAG
Pequeño pero hay que citar  60,000 tokens · citar=True  · acceso=False → viable=True  rojo=[] → Hybrid
Proyecto 2                 250,000 tokens · citar=True  · acceso=True  → viable=False rojo=['context_window',
                                                         'latency', 'lost_in_the_middle'] → RAG
Cómo leerla. Fíjate en el segundo caso: las cuatro restricciones técnicas pasan, pero hay que citar la fuente y un CAG no sabe de qué documento sale cada dato. Por eso recomienda Hybrid: lo estable por CAG, lo que hay que citar por RAG. (Salida resumida; el print real muestra los mismos valores.)

2.3 · Ingesta: el endpoint asíncrono

La ingesta es el pipeline offline: procesar una fuente puede tardar, así que el endpoint no espera. Responde 202 con un job_id y el cliente pregunta por el estado. Los comandos van con curl (macOS, Linux o Git Bash); debajo de cada uno está el equivalente para PowerShell. También se puede hacer desde el Swagger: http://localhost:8000/docs, sección ingestion, «Try it out».
POST /api/v1/ingestion/runs
diapo 14
Para qué sirve. Lanza la ingesta de una fuente del catálogo. Por dentro: comprueba que la fuente existe y es include, crea una fila en ingestion_jobs y deja el trabajo en segundo plano (loader → parser → Documents).
Comando
curl -s -X POST http://localhost:8000/api/v1/ingestion/runs \
  -H 'Content-Type: application/json' -d '{"source_name": "presupuestos_json"}'
En Windows (PowerShell)
$r = Invoke-RestMethod -Method Post -Uri http://localhost:8000/api/v1/ingestion/runs `
  -ContentType 'application/json' -Body '{"source_name":"presupuestos_json"}'
$r
Salida

source_name : presupuestos_json
status      : pending
Cómo leerla. pending no es un error: el trabajo acaba de empezar. Copia el job_id para el siguiente paso.

Para qué sirve. Para entender el informe, mira la tabla de fallos que devuelve Pandera con lazy=True. En docker compose exec estimator python:

        for p in sorted(pathlib.Path("data/seed/budgets").glob("*.json"))]

    BudgetRecord.validate(df, lazy=True)
except pa.errors.SchemaErrors as e:
    print(e.failure_cases[["column", "check", "index", "failure_case"]])
Salida

        None            column_in_schema  None        phases
        None            column_in_schema  None       contact

Cómo leerla.
  • lazy=True recoge todos los fallos de una vez; sin él, Pandera pararía en el primero y la política no podría repartir las filas.

La mapping table en Postgres
diapo 22
Para qué sirve. Comprueba cuántos mapeos hay guardados por tipo de entidad en la tabla pseudonym_mappings.
Comando
docker compose exec estimator-postgres psql -U estimator -d estimator \
  -c "SELECT entity_type, count(*) FROM pseudonym_mappings GROUP BY 1"
Salida
 entity_type | count 
-------------+-------
(0 rows)
Cómo leerla. 0 filas es lo esperado: la demo usa InMemoryMappingStore, que guarda en memoria y se pierde al acabar. En el pipeline real se usa PostgresMappingStore y ahí se guarda el hash (HMAC-SHA256) de cada valor, nunca el valor original. Esa tabla es la que hace posible el derecho al olvido.
